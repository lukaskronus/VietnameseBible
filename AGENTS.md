# AGENTS.md

Bilingual Vietnamese–English Bible site. Static site generated by `tools/*.py`;
the former PHP frontend (`index.php`, `test.php`) is gone.

Two datasets feed the same build chain, and they never mix:

| | Portable build | Public web version |
|---|---|---|
| Workflow | `.github/workflows/build.yml` | `.github/workflows/deploy.yml` |
| Trigger | `workflow_dispatch` only | push to `master` on `data/**`, `tools/**`, itself |
| Data | `data/xml/*.xml` (6 files, licensed) | `data/web_version/*.xml` (4 flat files, public domain, mixed formats: OSIS + USFX + Zefania) |
| Phase 1 | `tools/parse_bible.py` | `tools/parse_web.py` |
| Output | `site` + `site.zip` artifacts, 30-day retention | published to Wasmer Edge |

**The licensed set never leaves this repo.** `data/xml/` builds artifacts for
manual download; whoever takes them hosts them and carries the licensing risk.
Wasmer is only ever built from `data/web_version/`, which holds public-domain
editions (`vie1934`, `engbsb`, `engweb`, `engasv` today). Adding an edition
there is a licensing decision, made by the owner before any code change.

## Build and verify

Phases 2 and 3 are shared; only Phase 1 differs:

```sh
# portable (licensed)
python tools/parse_bible.py --data data --out build

# public web version (public domain)
python tools/parse_web.py --data data/web_version --out build

# shared
python tools/build_db.py --json build/bible.json --out build
python tools/build_site.py --json build/bible.json --index build/search_index.json \
  --out site --base-url "$SITE_BASE_URL" --base-path "$SITE_BASE_PATH"
```

Builds run on GitHub Actions only — the Python docstrings explicitly say local
machines are code storage, so do not run the pipeline locally. There is no test
suite, linter, or formatter; CI is the verification.

`parse_bible.py --data` accepts `data/` or `data/xml/` (it resolves `xml/`
itself). `parse_web.py` imports `VI_TITLES`/`EN_TITLES`/`TESTAMENT_LABELS` from
`parse_bible.py`, so book names and slugs are shared by both pipelines. It
parses three source formats: USFX (document-order walk over `<v>` markers),
OSIS (`div`/`chapter`/`verse` via `osisID` suffixes) and Zefania
(`BIBLEBOOK`/`CHAPTER`/`VERS` via number attributes); the format per edition
is declared in `TRANSLATIONS` inside it. `eng-web` ships a front matter, a
glossary and Apocrypha books that are skipped silently (`USFX_IGNORE`).

`build/` is gitignored; `site/` and `site.zip` are build output and are never
committed.

**Trigger rules differ, and they matter:**

- `build.yml` never runs on its own. Nothing is published to Wasmer by it.
- `deploy.yml` runs on every push to `master` touching `data/**` or
  `tools/**`. A CSS or JS edit under `tools/static/` therefore rebuilds and
  publishes the live site. Treat any change there as a release.
- Editing only `app.yaml`, `wasmer.toml`, or docs triggers no deploy (the
  `deploy.yml` path filter does not match them).

## Deployment

`deploy.yml` builds from `data/web_version/`, parses, builds the DB and site,
patches `version` in `wasmer.toml` to `0.1.<run_number>` (the registry rejects
republishing an existing version), then runs
`wasmer deploy --publish-package`. It needs the `WASMER_TOKEN` secret and only
runs from `master`; manual dispatch takes optional `base_url`/`base_path`
inputs, otherwise `vars.SITE_BASE_URL`/`vars.SITE_BASE_PATH` apply.

`wasmer.toml` maps `site/` to `/public` and `settings/` to `/settings`;
`app.yaml` pins the app name/owner/app_id. `build.yml` uploads `bible-parse`,
`bible-db`, `site`, and `site-zip` artifacts — the `site-zip` bundle is the
downloadable portable copy for nginx/docker hosting.

`.github/workflows/cleanup.yml` deletes all workflow runs older than 30 days,
weekly and on manual dispatch.

## Rules that span multiple files

- **Daily chapter formula** lives in `tools/static/daily.js`:
  `id = ((701 * days_since_unix_epoch_UTC + 123) % total_chapters) + 1`.
  701 is coprime to 1189, so every chapter appears once per cycle.
- **Book titles** live only in `tools/parse_bible.py` (`VI_TITLES`,
  `EN_TITLES`, `OSIS`); the XML stores numbers 1–66 only. Slugs derive from the
  Vietnamese titles via `slugify()`, so renaming a book changes its URLs.
- **Search folding** must match between `fold`/`tokenize` in
  `tools/build_db.py` and `fold`/`toks` in `tools/static/search.js`: NFD, strip
  combining marks, `đ/Đ/ð/Ð → d/D`, lowercase, `[a-z0-9]+` runs, tokens of at
  least 2 chars.
- **No translation codes in `tools/static/*.js`.** The default pair comes from
  the server-rendered `<option selected>` in the picker: `pair.js` reads it into
  `DEF_VI`/`DEF_EN`, and `book.js`/`daily.js` get the pair from `window.ktPair`,
  which is why both load after `pair.js` on every page that uses them. Both
  pipelines use different defaults (`vi1925`+`ennasb` vs `vie1934`+`engbsb`), so
  a literal in a static file would break one of them. Never reintroduce
  build-time string substitution for this.
- **Translation counts are computed, never written out.** The home masthead and
  the licence list derive their numbers from `meta.translations`; the web
  version currently has four editions, not six.

## Static site internals

- Chapter IDs are global canon order `1..1189`, not per book. The pairing
  switcher fetches `data/tr/<translation-code>/ch/<id>.json` for one VI and one
  EN translation; baked chapter pages contain only the default pair.
- The pair picker always renders both `<select>`s, even when a language has a
  single translation. On the web version that is one option each. This is
  deliberate — more public-domain editions are expected — so do not hide or
  remove the control to tidy it up.
- Client scripts read the base path from `<meta name="kt-base">`.
- `localStorage` keys: `kt-theme`, `kt-fs`, `kt-vi` and `kt-en` (translation
  codes), `kt-en-show` (`"0"` hides the English verses). Never reuse a key
  across two meanings.
- `build_site.py` minifies `tools/static/*.js` with a regex that strips
  everything after `//`. Never put `//` inside a JS string or regex (a URL such
  as `https://…` would be truncated at build time).
- Verse numbers are unioned across translations; a missing verse is `""`.
  Switcher views can therefore show verses absent from the default pair
  (e.g. 3 John 15), while baked pages skip them.
